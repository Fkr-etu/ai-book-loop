# Chapter workflow recovery

Chapter generation uses a durable run checkpoint in addition to immutable chapter versions.

## Run identity

A run is identified by `(book_id, chapter_number, idempotency_key)`. `GenerateChapter` derives a stable default key from the next expected chapter version, while callers can provide an explicit key when they need request-level idempotence.

A completed or `needs_review` run is returned without invoking Writer, Reviewer, Corrector, or Summarizer again. Once the chapter's `current_version` advances, a later generation request gets a new default key and therefore intentionally creates a new run/version.

## Checkpoints

The run persists:

- current step (`write`, `review`, `correct`, `summarize`);
- attempt/version number;
- draft;
- review and decision;
- summary;
- terminal status.

The workflow reserves an attempt before invoking an LLM. If the process stops after the chapter version is persisted but before the checkpoint advances, recovery loads that version instead of generating another draft.

The same rule applies to corrected versions: an already persisted version is reused during recovery.

## Failure semantics

Transient failures leave the run in `running` state so a subsequent request with the same idempotency key can resume it. A review that exhausts the retry budget ends in `needs_review`; it is not silently regenerated by a replay of the same key.

A successful run ends in `completed` only after the accepted chapter state and summary have been persisted. A terminal `needs_review` run does not advance the chapter's accepted version.

## Persistence and concurrency

The checkpoint store is backed by SQLite in the application container. Each checkpoint is committed independently, so a process restart observes only committed state. Same-process duplicate execution is serialized by a per-run lock.

The uniqueness constraint on `(book_id, chapter_number, idempotency_key)` makes run creation idempotent at the database boundary. It does **not** by itself claim execution of an already-created `running` run across processes.

Cross-process execution therefore does not yet provide an exactly-once guarantee. A future worker-oriented deployment should add explicit persistent run claiming/leases (or an equivalent transactional queue) before allowing horizontally concurrent generation workers.

## Known recovery gap

Review persistence and workflow-run checkpointing are currently separate writes. A crash after `save_review()` but before the run checkpoint can leave a persisted review without `run.review` being stored. Recovery may then invoke the Reviewer again for the same attempt.

This is a bounded duplicate-call window, not a chapter-version corruption path: chapter versions remain immutable. The preferred follow-up is either an atomic transaction covering review + run checkpoint or a deterministic review lookup/unique constraint that allows recovery to reuse an existing review.

## Guarantees today

The current implementation provides:

- durable step state in SQLite;
- immutable chapter-version history;
- stable request/run identity;
- recovery after version persistence without regenerating the same version;
- no replay of completed or terminal runs with the same idempotency key;
- bounded retry behavior;
- same-process duplicate execution serialization.

It does not yet provide distributed worker leasing or strict exactly-once LLM invocation semantics.
