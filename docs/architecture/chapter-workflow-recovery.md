# Chapter workflow recovery

Chapter generation uses a durable run checkpoint in addition to immutable chapter versions.

## Run identity

A run is identified by `(book_id, chapter_number, idempotency_key)`. `GenerateChapter` derives a stable default key from the next expected chapter version, while callers can provide an explicit key when they need request-level idempotence.

A completed run is returned without invoking Writer, Reviewer, Corrector, or Summarizer again. Once the chapter's `current_version` advances, a later generation request gets a new default key and therefore intentionally creates a new version.

## Checkpoints

The run persists:

- current step (`write`, `review`, `correct`, `summarize`)
- attempt/version number
- draft
- review and decision
- summary
- terminal status

The workflow reserves an attempt before invoking an LLM. If the process stops after the chapter version is persisted but before the checkpoint advances, recovery loads that version instead of generating another draft.

The same rule applies to corrected versions: an already persisted version is reused during recovery.

## Failure semantics

Transient failures leave the run in `running` state so a subsequent request with the same idempotency key can resume it. A review that exhausts the retry budget ends in `needs_review`; it is not silently regenerated by a replay of the same key.

The checkpoint store is backed by SQLite in the application container. SQLite commits each checkpoint independently, so a process restart observes only committed state. Same-process duplicate execution is serialized by a per-run lock.

Cross-process execution still depends on SQLite's single-writer serialization; a future worker-oriented deployment should move run claiming to an explicit lease/lock mechanism when generation becomes horizontally concurrent.
